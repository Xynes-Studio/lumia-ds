# XYN-SEC-004: safe SVG import

The audited boundary is a developer/CI SVG file entering `lumia-icon-import`, then a generated TypeScript module and React renderer. The existing importer copies SVG inner markup into a template literal and raw HTML sink. It also clears prior generated components before validating every input.

## Decision

Use a strict XML parser with a static SVG allowlist and generate JSX from the parsed tree. Values and text are emitted through `JSON.stringify`; source markup never becomes TypeScript syntax or raw HTML. Reject unsupported input rather than silently removing artwork, so a developer sees that an asset needs review. Validate and render the entire batch, including filename collisions, before replacing generated output.

Regex escaping alone would leave browser markup attacks and malformed XML unresolved. DOM-based sanitization followed by raw HTML generation would add a DOM implementation and retain an unnecessary rendering sink. `saxes` is already locked transitively in this repository; declaring it directly for the CLI supplies strict namespace-aware XML parsing without a new browser runtime. React and its typings are direct test dependencies for module-evaluation and server-rendering regressions.

Supported elements are static SVG geometry, groups, titles/descriptions, gradients/stops, clipping and masks. The policy excludes scripts, styles/inline CSS, event handlers, links/images/use, animation, foreign content, arbitrary namespaces, DTDs and processing instructions. Paint values accept static colors and exact local fragment references; masks/clips accept local fragments or `none`. Interpolation is rejected both before XML parsing and after entity decoding. JSX serializes text instead of parsing it as markup.

Per-file limits are 1 MiB, 4,096 elements, depth 32, 64 attributes per element and 16 KiB per attribute value. A batch permits at most 256 regular files and 16 MiB of actual bytes. Reads are bounded and use no-follow/nonblocking flags on POSIX systems. Filenames are limited to ASCII letters, numbers, spaces, underscores and hyphens; generated names/IDs must be unique. Numeric component names receive an identifier prefix.

## Compatibility and tests

Existing CLI component names, nested output layout, registry IDs, defaults and React SVG props remain supported for static artwork. The committed five-icon corpus is an acceptance fixture. Unsupported assets now fail closed and leave prior generated output intact. This is a deliberate security restriction; no permissive override is provided. Filesystem write failures are reported, but multi-file writes are not transactional.

Tests first reproduce interpolation, active markup and loss of prior output. Then test malformed/entity/namespace input, URL restrictions, actual React rendering of escaped content, filenames/collisions, batch preservation, source limits and command errors. Coverage includes the previously unmeasured executable and shared parsing module, with an 80% CLI gate. TypeScript checks both checked JavaScript and the security tests; the root type-check command invokes the CLI check. The corpus regression also semantically type-checks generated React components.

## Additional path

`@lumia-ui/icons build:icons` uses a separate SVGR/SVGO path. This change does not alter that build pipeline. A harmless isolated probe found that it retains script and foreign-object elements in generated JSX; no payload was executed. Apply the static SVG policy to that distinct pipeline under XYN-SEC-004-FU-1. The CLI fix must not be described as universal SVG sanitization.

No database, environment, authentication, deployment or public API change is required. Work is based on latest `develop` in isolated worktrees; no push or PR is authorized for this request.
